The engineering question

How can a small robotic platform stay attached to a ferromagnetic wall, move controllably, and support inspection tasks? Wall Patrol One brings adhesion, motion, electronics and software into one evolving system.

The current design has moved from an early track concept toward rubber-wheel rear drive with an electro-permanent magnetic chassis. Its story is a sequence of decisions and verification tasks, not a claim of a finished field-ready robot.

A system with distinct responsibilities

LayerCurrent directionResponsibility
High-level computationRaspberry Pi 5 · 8 GBHost-side software, interfaces and system coordination.
Real-time controlSTM32G474RET6 · RTOSMotor control, acquisition and low-level control tasks.
CommunicationCAN · isolated interfaceAn expandable interface between control and peripheral modules.
Physical platformWheels + magnetic chassisWall adhesion, locomotion and mechanical integration.

The interface architecture is a development baseline. It does not establish that every module is integrated and tested.

Magnetic adhesion & mechanical design

ANSYS Maxwell supports the magnetic adhesion study. The design considers the least favorable attachment condition and includes a pull-off-force margin relative to the platform weight.

A design criterion is not a measured adhesion result. Actual margin depends on the magnetic circuit, air gap, wall thickness and surface condition, as well as the real assembled mass. Mechanical mounting, wheel traction and load distribution must be checked together.

Control board · v0.3

The v0.3 architecture was frozen in August 2026 around the STM32G474RET6. Its development spans power domains, motor drive, isolated communication, sensing and debug access.

SubsystemRecorded components / interfaces
ControllerSTM32G474RET6 · 24 MHz crystal · SWD
Motor driveAT8236 H-bridge; left/right motor channels
CommunicationISO1042 isolated CAN · CH340 USB–serial
PowerIsolated DC–DC; 3.3 V regulation; distinct power/logic/CAN domains
Sensing & interfaceMPU6050 · OLED / HMI · button input

The board record covers schematic decisions and procurement changes. Firmware and wiring must follow the actual assembled board rather than an assumed generic STM32 pinout.

Firmware, interfaces & feedback

The current software direction combines Raspberry Pi 5 with STM32 control and a frozen V1 communication protocol. A virtual vehicle simulator supports early interface testing; an Android v1.0.0 installation has also been recorded.

Recent work focuses on motor-button debugging and OLED display of left/right real-time speed. These are active test tasks; requesting a behavior or generating code is not evidence that the motors have passed the corresponding hardware test.

Decisions between versions

  1. Early concept

    A smaller controller-led platform

    An initial STM32 + ESP8266 direction provided the starting point.

  2. System revision

    Raspberry Pi 5 + STM32

    Separate high-level computation from real-time control; retain CAN as the expansion direction.

  3. August 2026

    Control-board baseline v0.3

    Freeze the schematic architecture and record component substitutions against the actual build.

  4. Current

    Bring-up and integration

    Motor control, speed feedback, OLED and physical system debugging remain the focus.

Testing & what remains open

  • Keep a known-good wiring and firmware baseline for each hardware test.
  • Check supply rails, debug access and individual interfaces before combined motor operation.
  • Separate direction control, encoder feedback and displayed speed as distinct verification steps.
  • Validate magnetic attachment and mobility on representative wall conditions before making inspection-performance claims.

No measured payload, climbing speed, pull-off force or endurance is published on this page because the underlying test data were not supplied for this website update.
